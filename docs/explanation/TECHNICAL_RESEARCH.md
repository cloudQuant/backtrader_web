## 一、回测引擎性能优化

### 1.1 当前瓶颈分析

| 瓶颈 | 影响 | 根因 |
|------|------|------|
| Backtrader 单线程执行 | 回测速度受限于单核 | Backtrader 设计为单线程事件驱动 |
| Python GIL | 无法利用多核 CPU | CPython 全局解释器锁 |
| 数据加载 I/O | 大数据集加载慢 | 每次回测重新加载数据 |
| 指标计算 | 复杂指标计算耗时 | 纯 Python 实现 |

### 1.2 优化方案对比

| 方案 | 加速倍数 | 实施难度 | 兼容性 | 推荐阶段 |
|------|----------|----------|--------|----------|
| 数据预加载 + 缓存 | 2-3x | 低 | 完全兼容 | Phase 1 |
| Cython 编译关键路径 | 3-5x | 中 | 兼容 | Phase 1 |
| 多进程并行回测 | 线性扩展 | 中 | 兼容 | Phase 1（已有） |
| NumPy/Pandas 向量化 | 5-10x | 中 | 需适配 | Phase 2 |
| vectorbt 集成 | 10-100x | 高 | 新引擎 | Phase 3 |
| Rust 自研引擎 | 100-1000x | 极高 | 全新 | Phase 4+ |

### 1.3 推荐路径

```text
Phase 1: 数据缓存 + Cython 热点优化 + 多进程并行
    → 预期效果：3-5x 加速，零破坏性变更

Phase 2: 引入 vectorbt 作为"快速回测"模式
    → 预期效果：简单策略 100x 加速
    → 保留 Backtrader 作为"精确回测"模式

Phase 3+: 评估 Rust 引擎（如 nautilus_trader）
    → 仅在用户量和性能需求证明必要时启动
```

### 1.4 vectorbt 集成方案

```python
# 适配器模式：统一接口，底层可切换引擎
class BacktestEngine(Protocol):
    async def run(self, strategy: Strategy, data: DataFrame, params: dict) -> BacktestResult:
        ...

class BacktraderEngine(BacktestEngine):
    """精确模式：支持复杂策略、Tick 级别、多资产"""
    ...

class VectorbtEngine(BacktestEngine):
    """快速模式：向量化计算，适合简单策略批量回测"""
    ...

class EngineFactory:
    def select(self, strategy: Strategy) -> BacktestEngine:
        if strategy.complexity == "simple" and strategy.mode == "fast":
            return VectorbtEngine()
        return BacktraderEngine()
```

### 2.3 多模型策略

| 模型 | 用途 | 成本 | 延迟 |
|------|------|------|------|
| GPT-4o | 复杂策略生成、代码审查 | 高 | 中 |
| Claude 3.5 Sonnet | 策略分析、文档生成 | 中 | 低 |
| DeepSeek V3 | 中文策略生成（性价比） | 低 | 低 |
| Qwen 2.5 (本地) | 隐私敏感场景、离线使用 | 极低 | 取决于硬件 |
| 专用微调模型 | 策略评分、异常检测 | 低 | 极低 |

**统一接口方案**：LiteLLM 作为模型网关

```python
from litellm import acompletion

async def generate_strategy(prompt: str, model: str = "auto") -> str:
    """统一的策略生成接口，底层自动选择最优模型"""
    response = await acompletion(
        model=model,  # "gpt-4o" / "claude-3-5-sonnet" / "deepseek/deepseek-chat"
        messages=[{"role": "user", "content": prompt}],
        temperature=0.2,
    )
    return response.choices[0].message.content
```

### 2.4 RAG 增强方案

| 组件 | 当前方案 | 目标方案 | 收益 |
|------|----------|----------|------|
| 向量存储 | 内存/SQLite | ChromaDB / Milvus | 大规模检索 |
| 嵌入模型 | OpenAI ada | BGE-M3 (本地) | 成本降低 + 隐私 |
| 检索策略 | 简单相似度 | 混合检索（BM25 + 向量） | 准确率提升 |
| 上下文窗口 | 固定 chunks | 动态上下文组装 | 相关性提升 |

### 3.3 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 进程隔离 | 每个策略独立进程 | 单策略崩溃不影响其他 |
| 状态持久化 | 每笔订单写入 DB | 进程重启可恢复 |
| 心跳检测 | 5 秒间隔 | 快速发现连接断开 |
| 自动重连 | 指数退避 + 最大 5 次 | 避免雪崩 |
| 熔断机制 | 单策略亏损 > 阈值自动停止 | 保护资金 |

## 五、前端架构演进

### 5.1 当前技术栈评估

| 技术 | 评分 | 评价 |
|------|------|------|
| Vue 3 + Composition API | ★★★★★ | 优秀，生态成熟 |
| TypeScript (strict) | ★★★★★ | 必要，类型安全 |
| Element Plus | ★★★★☆ | 够用，但定制性有限 |
| Pinia | ★★★★★ | 轻量高效 |
| ECharts | ★★★★☆ | 功能强大，但金融图表不够专业 |
| Vite | ★★★★★ | 构建速度极快 |
| Tailwind CSS | ★★★★☆ | 灵活，但需要设计系统约束 |

### 5.2 前端优化方向

| 方向 | 方案 | 优先级 |
|------|------|--------|
| 金融图表升级 | TradingView Lightweight Charts / KLineChart | P1 |
| 设计系统 | 基于 Element Plus 的定制主题 + 组件库 | P0 |
| 性能优化 | 虚拟滚动 + 懒加载 + Web Worker | P1 |
| 离线能力 | Service Worker + IndexedDB 缓存 | P2 |
| 移动端 | 响应式优先，后期考虑 PWA | P2 |

### 5.3 图表技术选型

| 方案 | 优势 | 劣势 | 适用场景 |
|------|------|------|----------|
| ECharts（当前） | 功能全面、中文文档好 | 金融图表不够专业 | 通用图表 |
| TradingView Lightweight | 专业金融图表、轻量 | 功能相对少 | K线主图 |
| KLineChart | 国产、专为金融设计 | 社区较小 | K线 + 指标 |
| D3.js | 极度灵活 | 开发成本高 | 自定义可视化 |

**推荐**：ECharts（通用图表）+ KLineChart（专业 K 线）组合

## 六、安全架构

### 6.1 威胁模型

| 威胁 | 影响 | 概率 | 当前防护 | 需要加强 |
|------|------|------|----------|----------|
| 策略代码注入 | 极高 | 中 | 沙箱执行 | 加强沙箱隔离 |
| JWT 令牌泄露 | 高 | 中 | 短期令牌 + 刷新 | 增加设备绑定 |
| SQL 注入 | 高 | 低 | SQLAlchemy 参数化 | 已充分 |
| XSS 攻击 | 中 | 低 | 安全头 + CSP | 加强 CSP |
| API 滥用 | 中 | 高 | 速率限制 | 增加行为分析 |
| 数据泄露 | 极高 | 低 | 基础加密 | 全链路加密 |

### 6.2 策略代码沙箱

```text
当前：subprocess 执行 + 基础限制
目标：
├── Docker 容器隔离（每次回测独立容器）
├── 资源限制（CPU/内存/时间/网络）
├── 文件系统只读（除指定输出目录）
├── 网络隔离（禁止外部访问）
└── 系统调用白名单（seccomp）
```

## 八、技术选型决策框架

### 评估维度

对于每个技术选型决策，使用以下评分矩阵：

| 维度 | 权重 | 说明 |
|------|------|------|
| 成熟度 | 25% | 生产验证程度、社区规模 |
| 性能 | 20% | 满足当前和未来 2 年需求 |
| 可维护性 | 20% | 文档质量、学习曲线、人才市场 |
| 可替换性 | 15% | 是否容易替换为其他方案 |
| 成本 | 10% | 许可费、运维成本 |
| 安全性 | 10% | 已知漏洞、安全审计历史 |
