# 迭代155：工作区报表与优化契约收敛计划

## 1. 背景

当前项目已经有大量“优化计划”文档，但工作区报表与参数优化链路在前端依然存在几个现实问题：

- API 返回结构依赖 `Record<string, unknown>`，调用方缺乏稳定契约。
- `WorkspaceReportTab.vue` 仍存在局部 `Record<string, any>`，类型推导会在聚合计算时断掉。
- `workspace.settings.report_config` 与 `workspace.settings.optimization_config` 已被实际使用，但前端类型层没有正式表达。
- 类型边界不清晰会让后续报表列扩展、优化结果分析、默认配置持久化变得更脆弱。

这不是“代码风格”问题，而是主业务路径的可维护性问题。

## 2. 审查结论

本轮优先级按“收益 / 风险 / 改动面”综合排序如下：

| 优先级 | 方向 | 结论 |
| --- | --- | --- |
| P0 | 工作区前端契约 | 应优先收敛，能直接降低报表页和优化页的维护成本 |
| P1 | 运行时阻塞与日志规范 | 存在候选点，但需单独审视上下文后再改 |
| P1 | 单元/集成测试信号增强 | 有价值，但本轮未执行测试扩展 |
| P2 | 历史 TODO 清理 | 数量较多，需拆成独立工作包，不适合本轮泛化处理 |

## 3. 迭代目标

本轮目标不是“大而全重构”，而是把工作区报表/优化主链路的类型边界补齐到可继续演进的水平。

验收口径：

- `workspace` 类型层明确声明报表配置、优化展示配置、报表响应、优化响应。
- `workspaceApi` 不再对报表/优化核心接口使用宽泛匿名对象返回值。
- `WorkspaceReportTab.vue` 去掉当前关键路径上的 `Record<string, any>`，让聚合计算基于明确行类型工作。
- 迭代计划文档与目录索引同步更新。

状态：已完成

- 保持现有行为不变，只收紧类型边界，不引入额外交互改动。

状态：已完成

### WP3：后续候选项

- 把 `OptimizationConfigDialog.vue`、`BatchOptimizationConfigDialog.vue` 等同类组件中的 `Record<string, unknown>` 进一步细化。
- 对后端 `workspace_service` 的报表/优化响应补 `response_model`，把契约约束前移到 API 层。
- 针对工作区报表与优化结果补前端测试与契约测试。

状态：待下一轮
