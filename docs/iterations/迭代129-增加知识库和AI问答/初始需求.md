## 1. 背景

backtrader_web 当前已具备完善的量化交易、数据管理、策略研究与系统配置能力，但缺少一套面向业务知识沉淀与 AI 问答的统一能力。

原始诉求来自 ReqDocs 项目的“知识库 + AI 问答”能力迁移：

1. **知识库入口** 放在侧边栏 **“账户管理”与“系统设置”之间**。
2. **AI 问答入口** 放在侧边栏 **“首页”与“数据管理”之间**。
3. 将知识库与 AI 问答相关核心功能迁移到 backtrader_web，并能够正常使用。

> 说明：本轮文档整理过程中，已确认 `ReqDocs` 源码位于 `backtrader_web` 同级目录，并已完成关键模块核对；本文档在业务目标基础上，进一步结合了 backtrader_web 真实代码结构与 ReqDocs 源实现差异进行约束收敛。

---

## 2. 业务目标

本迭代不是简单“复制页面”，而是要在 **不破坏 backtrader_web 现有架构** 的前提下，引入一套可持续演进的知识管理与智能问答能力。

预期目标：

1. 用户可创建/管理知识库。
2. 用户可在知识库中维护文档与文件夹结构。
3. 用户可对知识库文档进行索引并发起基于知识库内容的 AI 问答。
4. AI 回答需要尽量给出引用来源，而不是仅返回无依据文本。
5. 新增功能需要遵循 backtrader_web 现有认证、路由、页面布局、后端分层和 UUID 主键等规范。

---

## 3. 本期范围定义

### 3.1 P0（本迭代必须完成）

1. **知识库管理**
   - 知识库列表/创建/编辑/删除
   - 每个知识库仅 owner 可管理，后续再考虑细粒度权限

2. **文档管理**
   - 文档/文件夹 CRUD
   - 树形组织
   - Markdown / TXT 优先支持
   - 文件导入至少支持 Markdown / TXT，PDF / DOCX 作为增强能力纳入 P1 条件交付

3. **索引与检索**
   - 文档分块
   - 向量化
   - 检索接口
   - 基于知识库的问答接口

4. **AI 问答主流程**
   - 新建对话
   - 多轮问答
   - 基于知识库检索上下文回答
   - 返回引用信息

5. **导航与页面接入**
   - 侧边栏增加“AI问答”与“知识库”入口
   - 更新 `AppLayout.vue`、前端路由、页面标题映射

### 3.2 P1（本迭代建议完成，但不阻塞 P0 上线）

1. AI 助手（内容改进、质量检查）
2. 模型管理后台能力（模型列表、默认模型、简单用量统计）
3. PDF / DOCX 导入增强
4. 混合搜索 / rerank 增强
5. 深度思考模式展示

### 3.3 明确不做

1. 与策略、回测、组合数据的深度联动
2. 多人协作编辑
3. 细粒度 RBAC 权限体系
4. 复杂工作流编排、异步任务中心、Celery 引入
5. 高级 BI/报表分析

## 4. 成功标准

从产品角度，需求达成的最低标准为：

1. 用户登录后可以从侧边栏进入“AI问答”和“知识库”。
2. 用户能够创建知识库并维护文档内容。
3. 文档能够被索引，且问答结果能基于知识库内容返回。
4. 问答结果包含可展示的引用来源。
5. 未登录用户无法访问；非 owner 用户不能访问私有知识库。
6. 文档与实现方案与 backtrader_web 现有代码模式一致，后续研发可直接按文档拆分实现。

## 5. 关键约束

1. **前端约束**
   - 现有主布局文件为 `src/frontend/src/components/common/AppLayout.vue`
   - 现有主路由文件为 `src/frontend/src/router/index.ts`
   - 新增页面必须沿用 Vue 3 + TypeScript + Element Plus + Pinia 模式

2. **后端约束**
   - API 统一挂载在 `app.include_router(api_router, prefix="/api/v1")`
   - 路由注册集中在 `src/backend/app/api/router.py`
   - 可选模块采用 `_register_optional_router()` 模式优雅注册
   - 业务分层遵循 `api -> services -> models/schemas`

3. **数据约束**
   - 现有主键模式以 `String(36)` UUID 为主
   - 用户表名为 `users`
   - 需要优先兼容现有 SQLAlchemy / Pydantic / async session 体系

4. **源实现约束**
   - ReqDocs 源仓已确认存在于同级目录，且知识库 / RAG / KB Chat / 模型管理源码已确认存在
   - 但迁移方式应为“能力抽取 + 结构适配”，不能机械照搬其项目结构与基础设施

## 6. 迁移裁剪原则

根据 ReqDocs 源码核对结果，正式开发时应采用以下裁剪原则：

### 6.1 可以直接借鉴的部分

1. `rag.py` / `rag_service.py` 的接口与检索主流程
2. `embedding_service.py` 中的 SiliconFlow embedding 封装
3. `surrealdb_service.py` 中的向量表初始化、写入、检索思路
4. `models.py` / `model_config.py` 中的预置模型配置结构
5. 前端 `KnowledgeBase.vue`、`KBChatPanel.vue`、`RAGChatPanel.vue`、`ModelSelector.vue` 的交互模式

### 6.2 不能直接照搬的部分

1. **领域模型命名**
   - ReqDocs 用 `projects + documents`
   - backtrader_web 目标用 `knowledge_bases + kb_documents`

2. **ID 体系**
   - ReqDocs 大量使用整数主键
   - backtrader_web 必须改为 UUID 字符串

3. **基础设施**
   - ReqDocs 使用 MySQL + MongoDB + Redis + Celery + SurrealDB
   - backtrader_web 本迭代仅应迁移必要能力，不引入 MongoDB / Celery / Redis 作为强依赖

4. **KB Chat 逻辑**
   - ReqDocs 的 `kb_chat_service.py` 当前更偏“读取最近文档内容作为上下文”
   - backtrader_web 应优先收敛到统一 RAG 检索链路，避免双套问答实现并存

---

## 7. 待澄清事项（开发前必须确认）

1. ReqDocs 中知识库存储的真实来源代码与版本基线
2. PDF / DOCX 是否作为本迭代上线阻塞条件
3. SurrealDB 是否作为本迭代强依赖；若环境不可用，是否允许只交付“无向量索引的占位能力”
4. AI 助手是否独立页面上线，还是作为 AI 问答页内二级能力上线
5. 模型管理是否面向普通用户开放，还是仅作为管理员配置能力
