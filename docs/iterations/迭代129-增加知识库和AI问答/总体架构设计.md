# 迭代129 - 增加知识库和 AI 问答 - 总体架构设计

> **文档状态**: 已优化，作为开发基线
> **最后更新**: 2026-04-23

---

## 1. 设计目标

在 backtrader_web 中新增“知识库”和“AI问答”能力，并满足以下要求：

1. 保持与现有前后端架构一致；
2. 不破坏现有系统启动与可选模块注册机制；
3. 形成“知识库管理 → 文档管理 → 索引 → 问答”的最小闭环；
4. 为后续 AI 助手、模型管理、策略知识联动预留扩展点。

---

## 2. 真实代码基线（必须遵守）

### 2.1 前端基线

| 项目 | 实际位置 |
|------|----------|
| 主布局 | `src/frontend/src/components/common/AppLayout.vue` |
| 主路由 | `src/frontend/src/router/index.ts` |
| API 客户端 | `src/frontend/src/api/index.ts` |
| 状态管理 | Pinia setup store 模式 |

### 2.2 后端基线

| 项目 | 实际位置 |
|------|----------|
| API 聚合路由 | `src/backend/app/api/router.py` |
| `/api/v1` 前缀挂载 | `src/backend/app/main.py` |
| ORM 模型 | `src/backend/app/models/` |
| Pydantic Schema | `src/backend/app/schemas/` |
| Service 层 | `src/backend/app/services/` |

### 2.3 关键约束

1. 新 API 文件目录应在 `app/api/` 下，而不是伪造 `app/api/v1/` 子目录；
2. 新业务路由推荐通过 `_register_optional_router()` 注册，避免依赖未安装时系统整体启动失败；
3. 主键默认采用 `String(36)` UUID；
4. 用户表为 `users`，相关外键必须对齐；
5. 前端新增菜单后必须同步更新 `AppLayout.vue` 的菜单、`currentRoute` 和 `pageTitle` 映射。

## 3. 功能边界与架构分层

### 3.1 业务模块拆分

| 模块 | 说明 | 迭代优先级 |
|------|------|------------|
| 知识库管理 | 知识库 CRUD、权限、设置 | P0 |
| 文档管理 | 文档/文件夹 CRUD、导入、组织结构 | P0 |
| 索引与检索 | 分块、embedding、向量存储、搜索 | P0 |
| AI问答 | 问答、对话、引用展示 | P0 |
| AI助手 | 内容改进、质量检查 | P1 |
| 模型管理 | 模型列表、默认模型、统计 | P1 |

### 3.2 分层原则

```
前端页面 / 组件
  -> Pinia store
  -> src/api/*.ts
  -> /api/v1/*
  -> app/api/*.py
  -> app/services/*.py
  -> app/models/*.py + app/schemas/*.py
  -> SQLite / SurrealDB / 外部模型服务
```

约束：

1. 页面不直接拼接复杂业务；
2. store 负责状态编排；
3. API 层负责鉴权、参数验证、错误码；
4. Service 层负责业务规则、外部依赖协调；
5. ORM 与 Schema 负责存储与输入输出边界。

## 4. 前端架构方案

### 4.1 侧边栏目标顺序

当前菜单（真实代码）：

```
首页 -> 数据管理 -> 行情报价 -> 策略研究 -> 策略交易
-> 策略管理 -> 组合管理 -> 账户管理 -> 系统设置
```

目标菜单：

```
首页 -> AI问答 -> 数据管理 -> 行情报价 -> 策略研究 -> 策略交易
-> 策略管理 -> 组合管理 -> 账户管理 -> 知识库 -> 系统设置
```

注意：

1. **AI问答** 必须位于“首页”和“数据管理”之间；
2. **知识库** 必须位于“账户管理”和“系统设置”之间；
3. `AppLayout.vue` 中的菜单、prefix 匹配和标题映射要一起改。

### 4.2 推荐路由

| 路由 | 页面 | 说明 |

| `/ai-chat` | `AIChatPage.vue` | AI问答主入口（侧边栏） |

| `/knowledge-base/:id` | `KnowledgeBasePage.vue` | 知识库详情/当前选中知识库 |
| `/ai-assistant` | `AIAssistantPage.vue` | P1，可独立页面或二级入口 |

建议：

- **P0** 只把 `/ai-chat` 与 `/knowledge-base` 放进主导航；
- `AIAssistantPage.vue` 作为 P1 能力，不要求本轮进入侧边栏。

## 5. 后端架构方案

### 5.1 路由注册方式

建议新增以下 API 模块：

```
src/backend/app/api/
├── knowledge_base.py
├── kb_chat.py
├── rag.py
├── ai_assistant.py              # P1
└── models.py                    # P1
```

推荐在 `app/api/router.py` 中使用与现有可选模块一致的方式注册：

```python
_register_optional_router(
    "knowledge_base",
    "app.api.knowledge_base",
    prefix="/knowledge-base",
    tags=["Knowledge Base"],
)
```

这样可以保证：

1. 依赖未就绪时不阻塞整个系统启动；
2. 与现有 `data / monitoring / quote / paper_trading` 等模块风格一致。

### 5.1.1 ReqDocs 源码映射事实

ReqDocs 中真实存在的对应后端入口：

| ReqDocs 源文件 | 实际职责 | 迁移建议 |
|----------------|----------|----------|
| `backend/app/api/v1/rag.py` | RAG 检索、问答、索引、统计 | 作为 `rag.py` 主要参考来源 |
| `backend/app/api/v1/kb_chat.py` | 对话列表、创建、删除、历史、发送消息 | 作为 `kb_chat.py` 参考来源，但需改成 UUID / 新权限模式 |
| `backend/app/api/v1/models.py` | 模型列表、分类、聊天模型、usage stats | 作为 P1 `models.py` 参考来源 |
| `backend/app/services/rag_service.py` | 向量检索 + prompt 拼装 + LLM 回答 | 可抽取核心逻辑，但需把 `project_id` 改为 `knowledge_base_id` |
| `backend/app/services/kb_chat_service.py` | 对话管理 + 传统知识库问答 | 需要保留会话管理思路，但问答逻辑建议与 RAGService 收敛 |
| `backend/app/services/embedding_service.py` | SiliconFlow embedding + chunk 计数 | 高复用价值 |
| `backend/app/services/surrealdb_service.py` | SurrealDB schema、写入、检索 | 高复用价值，但需字段重命名 |
| `backend/app/services/ai_assistant.py` | AI助手统一能力入口 | 作为 P1 参考来源 |

关键结论：

1. ReqDocs 中 **RAG** 与 **KB Chat** 是两条并行能力线；
2. `kb_chat_service.py` 当前更像“会话管理 + 文档上下文问答”，并不等同于完整 RAG；
3. 在 backtrader_web 中建议把“检索与回答”能力统一收口到 `RAGService`，`KBChatService` 只负责对话与消息管理。

### 5.2 Service 层建议

```
src/backend/app/services/
├── knowledge_base_service.py
├── document_service.py
├── chunk_service.py
├── embedding_service.py

```

职责边界：

| Service | 主要职责 |
|---------|----------|
| KnowledgeBaseService | 知识库 CRUD、权限校验 |
| DocumentService | 文档/文件夹 CRUD、导入解析、树结构调整 |
| ChunkService | 文档分块与 token 统计 |
| EmbeddingService | embedding 调用封装 |
| SurrealDBService | 向量写入、删除、搜索 |
| RAGService | 检索、上下文组装、回答生成 |
| KBChatService | 对话、消息、历史记录 |
| AIAssistantService | 内容改进、质量检查（P1） |
| ModelManagerService | 模型配置和默认模型（P1） |

## 6. 数据与外部依赖架构

### 6.1 存储分工

| 存储 | 用途 |
|------|------|
| SQLite / 主业务数据库 | 知识库、文档、对话、消息、模型配置等结构化数据 |
| SurrealDB | 文档 chunk 与 embedding 向量检索 |

### 6.2 外部模型服务

| 服务 | 用途 |
|------|------|
| SiliconFlow | chat / embedding / rerank 统一接入 |

### 6.3 设计理由

1. 保持结构化数据继续在现有主数据库中管理，降低系统割裂；
2. 向量检索单独交给 SurrealDB，避免在主业务库内做不成熟的拼接；
3. 模型接入统一收敛到一个 Provider，降低配置复杂度。

### 6.4 ReqDocs 源实现与本项目的关键差异

| 维度 | ReqDocs | backtrader_web 目标 |
|------|---------|---------------------|
| 领域主对象 | `projects` | `knowledge_bases` |
| 文档主表 | `documents` | `kb_documents` |
| 会话主键 | `Integer` | `String(36)` UUID |
| 用户主键 | `Integer` | `String(36)` UUID |
| 文档内容存储 | MySQL + MongoDB 双写 | 以主业务数据库 + 文件系统/必要扩展为主 |
| 后台任务 | Celery | 本迭代不引入 |
| 缓存 | Redis | 本迭代不强依赖 |

因此，本迭代不是“按文件复制 ReqDocs”，而是：

1. 复用其 RAG / embedding / SurrealDB / 模型管理的能力设计；
2. 放弃其过重的 MySQL + MongoDB + Celery 运行方式；
3. 在 backtrader_web 中按 UUID + 现有 API 注册模式重构落地。

## 7. 核心流程

### 7.1 知识库文档索引流程

```
用户上传/编辑文档
  -> DocumentService 保存文档
  -> ChunkService 分块
  -> EmbeddingService 生成 embedding
  -> SurrealDBService 写入向量记录
  -> 更新文档 indexed_at / index_status
```

### 7.2 AI问答流程

```
用户发起问题
  -> KBChatService / RAGService 接收请求
  -> EmbeddingService 向量化问题
  -> SurrealDBService 检索候选 chunk
  -> RAGService 组装上下文
  -> 模型生成回答
  -> 保存对话消息
  -> 返回 answer + citations + tokens_used
```

## 8. 迁移策略

### 8.1 不建议的做法

1. 直接把 ReqDocs 的目录原样拷入项目；
2. 新起一套与现有前后端风格完全不同的架构；
3. 在 P0 阶段引入复杂权限、异步任务编排和大而全模型管理。

### 8.2 推荐做法

1. 迁移“能力”，而不是迁移“目录”；
2. 所有路径、命名、路由注册方式以 backtrader_web 真实代码为准；
3. 先交付最小闭环，再逐步扩展 AI助手 / 模型管理 / 高级检索。
4. 采用以下语义映射：

| ReqDocs 源对象 | backtrader_web 目标对象 |
|----------------|-------------------------|
| Project | KnowledgeBase |
| Document | KBDocument |
| KBConversation | ChatConversation |
| KBChatMessage | ChatMessage |
| ModelConfig / PRESET_MODELS | ModelConfig / 预置模型配置 |

5. 对于 `KBChatService`，保留“会话生命周期管理”部分；
   对于“回答生成”部分，应优先与 `RAGService` 统一，避免双套问答实现并存。

---

## 9. 本迭代不做项

1. 与 workspace / strategy / backtest 形成自动知识联动；
2. 文档版本历史与 diff；
3. 实时协作与评论；
4. 复杂多租户权限；
5. 后台批处理任务中心。

---

## 10. 架构风险与建议

| 风险 | 影响 | 建议 |
|------|------|------|
| ReqDocs 源实现未直接在本 workspace 可见 | 文件级迁移描述可能失真 | 开发前补做源实现核对 |
| SurrealDB 未就绪 | 索引/检索功能无法落地 | 尽早准备本地与 CI 环境；P0 中优先验证连通性 |
| PDF / DOCX 导入依赖复杂 | 拉长交付周期 | 作为 P1，不阻塞 P0 主流程 |
| AI 助手范围过大 | 拖慢主线交付 | 作为 P1 能力分离 |

结论：**本迭代的工程主线应聚焦 P0 最小闭环，而不是把所有 AI 增强能力一次性打满。**
