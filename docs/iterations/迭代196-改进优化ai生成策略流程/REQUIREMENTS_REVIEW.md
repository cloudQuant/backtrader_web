# 迭代 196 需求集评审与改进建议

> 文档性质：独立评审意见，不是需求、设计或验收结论；采纳与否须在迭代治理中留痕。
> 评审对象：本目录下 `README.md`、`REQUIREMENTS.md`、`CURRENT_STATE_AUDIT.md`、`ARTICLE_REVIEW.md`、`DESIGN.md`、`ACCEPTANCE.md`（2026-09-04 基线）。
> 评审日期：2026-09-04。
> 代码抽查基线：`HEAD = a18bcf52`，与 CURRENT_STATE_AUDIT 声明一致。

## 1. 总体结论

这套文档的**分析质量明显高于常见需求文档**：现状审计的行号级论断经抽查全部属实（见第 6 节）；文章观点做了证据分级和反需求处理；验收文档坚持"负例先于漂亮结果""P0 UNKNOWN 即 NO-GO"；三份决定（实现验收/协议启用/候选晋级）分离是正确的治理设计。

但作为**可以开工的需求基线**，仍有 4 个 A 类问题需要先裁决，8 个 B 类问题应在开工前修订进文档，4 个 C 类建议可登记为 P1。核心风险不在"想得不够多"，而恰恰在**范围与产品形态的匹配**：

1. **A1 范围过载 + 全有全无**：P0 约 90 条功能需求、7 个切片含 4 个 XL 项，且文档明确"砍掉密封/租户/密钥/沙箱/审计/持久任务就不能称可信 v2"。在容量未确认的情况下，这等于"要么全做完、要么整个迭代不算数"，缺少中间退路。
2. **A2 角色模型与单人自托管形态冲突**：需求假设研究员/审批人/管理员等身份可分离，但本产品的主部署形态是自托管单用户；单人环境下"独立审批、职责分离、四眼"物理上无法满足，文档没有给出该形态下的降级语义和残余风险披露。
3. **A3 部署拓扑约束未成为需求**：密封评估要求独立 DB role、队列、对象存储凭据，而 SQLite 没有 role 概念；NFR-COMP-001 又要求 SQLite/PostgreSQL/MySQL 全通过。二者未调和，"什么拓扑支持什么能力、不满足时如何 fail-closed"没有写成需求。
4. **A4 账本不可变 vs 隐私删除**只有一句话，没有形成需求。

**建议**：先完成第 7 节的处置清单再进入 S1 开发；B 类修订只改文档，成本低，应与 A 类裁决一并完成。

## 2. 值得保持的优点（防止修订时丢失）

- 审计论断可复核：行号、SHA、证据边界、"未使用用户凭据不得声称已验收"的纪律；
- 文章数字不入库：十倍效率、替代人数等 C 级断言全部排除在验收阈值之外；
- T0～T3 证据等级 + 三份决定分离 + `NOT RUN / NO_GO` 默认值；
- 对既有资产的处理克制：复用 `purgedcv`/lease/CAS/沙箱基础，先修 `var_sharpe` 语义再进门禁，而不是重写；
- 术语迁移诚实：旧 `out_of_sample` 只许解释为 `iteration_validation/legacy_oos`。

## 3. A 类问题：开工前必须裁决

### A1：P0 范围过载，缺少"最小可信切片"与暂停判据

**位置**：README 7.1、13.2（Release cut line）、DESIGN 13.1。

**问题**：

- P0 覆盖预注册、四分区、冻结、账本、DSR、谱系、持久任务、可信确认/审批、密钥治理、沙箱全链路、证据工作台、灰度回滚共 11 大项；DESIGN 13.1 中 S3、Sandbox、S5 均为 XL，且"实际人员与迭代容量需要团队确认"。
- 13.2 同时规定：容量不足时**不能**从 Cut A 删除密封、租户、密钥、真实沙箱、审计、持久任务，只能"缩小批准范围或保持旗标关闭"。也就是说容量不足的唯一出路是"做了但不开"——已经投入的 XL 工作量无法分批兑现为任何可用的中间产物。

**影响**：这是本迭代最大的交付风险。一旦中途容量见底，迭代将处于"做了一半、不可声称可信、也不能验收"的悬置态；且没有预先定义的暂停/重切分协议，届时只能临场讨价还价，正是本迭代想消灭的"见结果后放宽标准"。

**建议**（任选其一，需在 G0 留痕）：

1. **显式拆为 196a/196b 两个迭代**：
   - 196a 可信地基：S0 + S1 + S2 + S4（身份、账本、统计门、持久任务）+ 语义迁移；其交付声明限定为"探索过程完整留痕、搜索修正、运行可恢复"，**不声称密封独立性**；
   - 196b 密封与执行边界：S3 + Sandbox 全链路 + S5/S6；
   - 每个子迭代自带各自的 G 门与三份决定模板子集。
2. 若坚持单迭代，则在 **S0 退出条件中强制加入容量评估结论**（按 13.1 表逐行给出可用人日与并行度），并预先签署"容量不足时的降序裁剪顺序"：先砍 S5 的证据工作台范围（保留最小五区块），再砍 S6 灰度自动化程度，**密封、租户、密钥、沙箱、审计、持久任务不可裁**——把"不可裁"从口号变成预先签署的范围合同。

### A2：角色模型不适配单人/自托管部署

**位置**：REQUIREMENTS 3（用户与职责）、FR-GATE-004～007、FR-GATE-009、AC-APP-001～002。

**问题**：

- 职责表定义了研究员、评审人、风险/实盘审批人、管理员、审计员等角色，并要求审批身份来自认证上下文、挑战可验证、（P1）四眼。
- 本产品的主部署形态是自托管、通常单用户：研究员 = 审批人 = 管理员 = 同一登录身份。此时"独立责任主体"在物理上不存在；AC-APP-002 的"合格审批角色完成显式挑战"会退化为"自己挑战自己"。
- 文档通篇未定义单用户拓扑下的语义：哪些门禁自动降级为 `UNSUPPORTED_SINGLE_USER`、单人审批的残余风险如何向用户披露、是否用**强制冷却期 + 逐项挑战 + 证据哈希绑定**作为单人场景的替代性保障。

**影响**：若不处理，P0 全部实现后，单人用户的晋级链仍然"形式合规、实质自批"，与迭代目标 O5（晋级决定有独立责任主体）直接冲突；而且这是产品形态问题，不是实现阶段能顺手补的。

**建议**：

- 在 REQUIREMENTS 3 增加拓扑化职责说明：多用户部署按现有角色表；单用户部署声明"人类责任与 AI/系统责任分离仍然强制（AI 不得自批、前端不得伪造、证据哈希绑定、冷却期），人类内部职责分离不可强制，残余风险必须在审批界面显式披露"；
- 增加一条需求（建议编号 `FR-GATE-010`，P0）：单用户环境下实盘批准必须包含强制冷却期（批准请求创建与可提交之间存在策略规定的最小间隔）、逐项挑战回答和证据包哈希回显，且决定记录中标记 `single_actor=true` 以便审计与界面披露；
- AC-APP-002 增加单用户分支场景。

### A3：部署拓扑与 DB 引擎约束没有成为需求

**位置**：FR-DATA-013、NFR-COMP-001、DESIGN 3.2。

**问题**：

- FR-DATA-013 要求 Independent Evaluator 使用"独立 DB role、对象存储凭据与专用队列"；
- SQLite 无 DB role/用户体系，单进程部署也无独立队列；
- NFR-COMP-001 要求"SQLite/PostgreSQL/MySQL 均通过迁移与核心契约测试"。
- 三者之间没有调和条款：没有任何一处声明"哪种部署拓扑支持密封评估，不满足时密封门如何表达"。DESIGN 3.2 说"单进程函数调用仅可做 unit test"，等于隐式宣布单进程部署永远拿不到密封证据，但这个结论没有写回需求，也没有定义此时用户看到什么（应当是 `BLOCKED` + 原因，而不是静默不可用）。

**影响**：实现者会在 SQLite 开发环境里反复撞上"无法满足自己写的 P0"的困境；或者更糟——为了测试通过而弱化隔离要求。

**建议**：新增需求族（建议 `FR-DEP-001～003`，P0）：

- `FR-DEP-001`：系统必须声明并运行时检测部署拓扑分级（建议：`dev-single-process` / `single-node-docker` / `multi-service`），每个分级有明确能力矩阵（能否签发密封授权、能否执行真实沙箱全链路、审批挑战是否完整）；
- `FR-DEP-002`：当前拓扑不满足某能力时，对应门禁必须返回 `BLOCKED + 拓扑原因`，不得静默跳过或降级为假通过；
- `FR-DEP-003`：明确 SQLite 仅承诺迁移与核心契约测试通过，密封评估、租户凭据隔离等依赖 DB role 的能力要求 PostgreSQL/MySQL 多服务拓扑；并相应修订 NFR-COMP-001 的措辞，把"迁移与核心契约"和"安全隔离契约"分开表述。

### A4：账本不可变与隐私删除的冲突只有一句话

**位置**：FR-LEDGER-003（禁止硬删除）对比 REQUIREMENTS 10 末段（"删除用户数据时保留最小审计墓碑"）。

**问题**：

- 实验账本、模型调用记录保存了策略代码、用户研究问题、prompt 哈希等与用户强关联的内容；"追加式、不得删除"与用户数据删除请求（无论来自法规还是自托管用户自主清理）直接冲突。
- 目前只有一句"保留不含个人/秘密的最小审计墓碑或按法律/组织政策执行"，没有定义：哪些字段构成"最小墓碑"、证据包导出在删除请求后如何处理、已引用的 artifact 是否级联失效。

**影响**：这是治理债，不是本迭代必须完整解决，但**必须立项留痕**，否则"不可变账本"会在第一次真实删除请求时被临时破坏，恰好破坏本迭代的审计完整性目标。

**建议**：在 REQUIREMENTS 增加 `FR-PRIV-001`（P1，明确登记）：定义账本擦除的墓碑字段集、证据包级联策略与审批记录，并声明本迭代实现"逻辑删除 + 导出排除"，物理擦除方案移交后续治理迭代；在 ACCEPTANCE 10.1 的 `DEFERRED_P1` 清单中显式列出。

## 4. B 类问题：开工前应修订进文档

### B1：FR-HYP-004 的失效字段清单与验收场景、与 GAP-05 策略不一致

**位置**：REQUIREMENTS FR-HYP-004；README GAP-05；ACCEPTANCE AC-HYP-002。

- FR-HYP-004 列举的受约束字段为"prompt、标的、频率、日期、成本、质量门、OOS/稳健性配置、搜索预算或数据策略"，**缺少主指标/次指标、失效条件、`workflow_steps`**；而 AC-HYP-002 逐项变更清单里明确包含"主指标"和"workflow"。
- 同时 README GAP-05 的方向是"用完整规范化请求哈希绑定确认与任务"。枚举字段清单与全量哈希绑定是两种策略并存，实现者会困惑以哪个为准，且枚举清单天然会漏（本条就是证据）。

**修订建议**：FR-HYP-004 改为"以规范化请求内容哈希为唯一权威：确认后的请求中任何使哈希变化的字段改动都使确认失效；以下清单仅为示例说明……"，并把主指标、失效条件、`workflow_steps`、执行/沙箱策略补入示例清单。

### B2：AC-I18N-001 没有对应的功能需求

**位置**：ACCEPTANCE 5.10 的 AC-I18N-001；REQUIREMENTS 6.7 无 i18n 条目（DESIGN 9.5 提及但需求缺位）。

验收文档自己规定"任何新增需求若没有验收方法不能标为 P0"；反向的孤儿场景（有验收、无需求）同样破坏追踪合同。建议补 `FR-UI-014`（P0）：所有 stage、gate 状态、错误码、按钮与空态文案必须走 i18n，未知服务端错误保留 code 与 trace ID。

### B3：需求追踪矩阵是区间级映射，无法机器校验单条 FR 覆盖

**位置**：ACCEPTANCE 6（如 `FR-DATA-001～013 → AC-DATA-001～004、AC-SEAL-001～006、AC-T3-001`）。

G0 要求"任何 P0 无法映射到具名场景即 G0 FAIL"，但区间映射无法判断 `FR-DATA-002`（快照元数据）这类中间条目到底被哪个场景覆盖。抽查即可见疑点：`FR-DATA-002` 的供应商/时区/复权/许可标签等字段仅被 AC-DATA-002 的"内容哈希一致"间接覆盖，许可标签（`license_tags`）无场景直接断言。

**修订建议**：把矩阵展开为逐条 `FR-ID → 场景 ID` 表（约 90 行，一次性成本），作为 G0 的门禁输入；无法映射的行立即暴露为需求缺口。

### B4：AC-MIG-003 的"关键差异"未定义

**位置**：ACCEPTANCE AC-MIG-003、MIG-002。

"任何关键差异使 v2 promotion BLOCKED"——但什么算关键差异（状态机差异？指标数值差异？计数差异？浮点容差内差异？）没有预注册。这正是文档自己反复强调的原则："容差必须在运行前定义，不能见结果后放宽"。

**修订建议**：在 MIG-002/AC-MIG-003 中预定义差异分级：`BLOCKING`（状态、计数、门禁结论、身份哈希不一致）与 `NON_BLOCKING`（时间戳、展示文案、容差内数值），并规定 NON_BLOCKING 差异需登记样例与处理决定。

### B5：偏差/豁免流程没有落点需求

**位置**：ACCEPTANCE 10.2（"确需发布必须另做风险批准"）；DESIGN 17（"明确 exception 流程"）；但 REQUIREMENTS 与 DESIGN 均未定义该流程的记录结构。

没有合同的豁免条款就是后门。建议补 `FR-GATE-011`（P0，可极简）：任何偏差批准必须记录偏差对象、理由、批准人、生效范围与失效时间，追加写入人工决定表，且不得把被偏差的门显示为 PASS。

### B6：配置档案 YAML → DB 迁移缺少验收场景

**位置**：FR-SEC-011、MIG-004、DESIGN 12.2（"profile 迁移只允许白名单字段，疑似 secret 丢弃并告警"）；ACCEPTANCE 只有 AC-TENANT-001/002（测新行为）与 AC-MIG-002（测 workspace JSON，不是 profile）。

建议补 `AC-MIG-005`：构造含白名单字段、疑似 secret、超深嵌套的存量 YAML 档案，迁移后断言白名单字段完整、疑似 secret 被丢弃且产生告警与审计记录、所有权落到正确 user。

### B7：命名不一致（低危但影响检索与评审效率）

- 表名前缀混用 `ai_research_*`（DESIGN 5.1～5.3、5.7～5.12）与 `ai_strategy_research_*`（DESIGN 5.4～5.6），建议 S0 统一为一个前缀；
- 术语"前向观察（Forward Shadow）"（REQUIREMENTS 4）与"forward observation"（DESIGN 5.3 表名 `ai_research_forward_observation_epochs`）并存，建议术语表锁定唯一中英文对；
- 目录名"迭代196-改进优化ai生成策略流程"与文档标题"可信 AI 策略研究流程"不一致（目录名不宜改以免断链，在 README 加一句说明即可）。

### B8：README"冷环境可重放率 100%"与模型不可冻结的边界未写明

**位置**：README 9（成功指标）对比 ARTICLE_REVIEW P6。

可重放对象实际是**冻结候选**（代码/参数/数据/环境），不包括 LLM 生成过程本身；该指标行目前只注明了行情数据的快照读取边界。建议在指标行补一句："重放对象为冻结候选与其证据链；生成阶段的模型输出不可冻结，按 ARTICLE_REVIEW P6 披露。"避免实现验收时被按字面 challenge。

## 5. C 类建议：登记为 P1 候选

1. **C1 用户侧护栏指标**：全部成功指标均为流程可信性指标，缺少可用性回归护栏。建议至少 1 条：从打开页面到提交研究任务的操作步数/必填项数量相对 v1 基线的上限，以及任务提交 API 的延迟基线（与 NFR-PERF 合写）。预注册、预检、确认必然增加操作步骤，没有护栏就无法发现"更可信但不可用"。
2. **C2 证据存储的备份与恢复**：追加式账本与证据包是本迭代的核心资产，但没有任何备份/恢复演练要求。建议在 NFR-AUD 增加一条（可 P1）：artifact/账本存储具备可演练的备份与恢复路径，恢复后内容哈希校验通过。
3. **C3 配额与限流的优先级复核**：`FR-TASK-009`（预算、队列优先级、并发配额）为 P1，但多租户下 LLM 调用与回测是真实成本项，滥用防护（至少是并发配额 + 预算硬停）建议评估提前到 P0，或明确声明依赖现有 `ai_chat_service` 预算机制在 FR-PIPE-010 中兜底。
4. **C4 消歧与备注**：发布门 `G0～G5` 与研究门禁 `gate_code` 中文都叫"门"，建议在 README 加消歧句；`FR-LEDGER-005` 的 DSR"基准"输入建议在 REQUIREMENTS 9 明确归属 Promotion Policy 的版本化字段，避免实现时悬空。
