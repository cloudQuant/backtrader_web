## 1. 目标与建议

建立项目自己的统一数据服务，使页面查询和策略准备都执行同一条路径：**按请求语义查询本地数据库 → 判断完整性和时效 → 只补齐缺失或需要刷新的数据 → 校验并持久化 → 从已提交数据返回结果或生成研究快照**。相同条件的后续请求在本地数据仍满足要求时不再联网。

推荐建设模块化数据中台：在现有 FastAPI 项目内形成清晰的目录、查询、采集、质量、存储和快照模块；同步 SDK 调用由有界采集 worker 执行，OpenBB 放在独立依赖运行环境。沿用现有 MySQL 数据仓库及应用数据库，初期不引入 Kafka、ClickHouse、Airflow 集群或数据湖管理平台。达到容量阈值后再扩展存储。

OpenBB 作为一个可插拔数据获取入口，其下仍需区分 `yfinance`、`fmp` 等真实供应商。它的 Provider、标准数据模型及 TET 流程值得采用；本项目负责落库、缺口、版本、权限和研究可复现性。OpenBB 供应商能力依赖所装扩展、具体市场和订阅，不能把“有该模型”解释成“能为中国七类资产提供等价备用数据”。参见 [OpenBB 架构](https://docs.openbb.co/odp/python/developer/architecture_overview) 和 [数据供应商说明](https://docs.openbb.co/odp/python/faqs/data_providers)。

## 3. 范围冻结

- 七类资产全部纳入：股票、期货、债券、基金、期权、外汇、数字货币。每类保留现有真实数据功能并接入统一查询与持久化；不得以股票通过代表七类通过。
- 行情页保留快照、历史、指标、标的搜索、覆盖矩阵及关联表；分别处理行情序列、期权链、CME 持仓、估值、结算和目录主题，避免把不同数据强行转成 OHLCV。
- 策略页的 `1d/1h/30m/5m`，行情页的日/周/月，以及已有本地 CSV 都进入能力登记。供应商没有相应历史或频率时如实阻断，不能用日线伪造分钟线。
- 数据完整性、许可、落库和快照门禁是统一服务的基本要求。缺权限或缺真实环境的验收为 `BLOCKED`，不能写成通过。
- OpenBB 至少需要一个真实供应商完成“采集—持久化—复用—策略数据准备”全链验收；不能只提交一个未启用 adapter。

“当前支持的全部数据类型”不等于一次改写全部 AkShare 脚本，也不表示已经具备七类资产的所有金融分析能力。页面中的主题卡片有些只是字段可用性与关联表提示；它们全部保留并登记，实际数据承诺见 DATA_SCOPE。已有功能不能被悄悄列为后续阶段。

## 4. 关键架构决定

| 决定 | 原因与结果 |
| --- | --- |
| 延续迭代 189 三层目录 | 分开数据来源、逻辑数据集和物理数据库，避免 SDK 名变成数据库名 |
| 本地事实表为权威，缓存只加速 | 应用重启、Redis 清空后仍可复用；覆盖记录必须能回溯到已提交数据 |
| 查询与采集分开 | 页面先展示合格本地数据；缺口变为可恢复任务，慢来源不会长期占用 API 请求 |
| 来源按能力和语义选择 | 同一币种、合约、复权和报价口径才允许切换；不能把 BTCJPY 换成 BTCUSD |
| 完成落库后才宣告数据已就绪 | 写入失败保留任务和失败状态，避免网络成功却每次重抓 |
| 策略只消费冻结工件 | 预检、实际运行和重放使用相同内容哈希，供应商后续修订不改变旧实验 |
| 196 保留研究权限权威 | 普通行情接口不能成为 Explorer 读取密封数据的旁路 |
