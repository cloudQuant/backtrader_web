# 迭代 197：需求文档

> 状态：设计基线。优先级 P0 为完整迭代必须实现并验收；P1 为后续增强，不用于豁免 P0。
> 已确认：覆盖两个目标页面当前支持的全部数据类型；具体边界以 [DATA_SCOPE.md](DATA_SCOPE.md) 为准。

## 1. 问题与业务目标

当前同一份数据可能分别从行情页面、脚本、预检或 CSV 运行路径读取。用户无法稳定判断本地是否完整、在线是否已落库、下一次是否还需联网，也难以保证研究时使用的内容就是预检过的内容。

迭代 197 的目标是把“用户查询数据”转为“请求一个有明确身份、时间、质量和权限的数据集版本”。系统优先复用本地事实；在条件允许时自动补齐并保存，成功之后页面和研究共同消费。用户应看懂数据在哪里缺、正在补什么、何时更新、能否用于研究。

## 2. 用户与核心旅程

| 用户 | 旅程 | 可观察结果 |
| --- | --- | --- |
| 行情查看者 | 选择资产/标的/时间 → 查询 | 本地满足时直接返回，界面显示时间、来源及完整度 |
| 行情查看者 | 本地部分缺失 → 自动补齐 | 已有部分先显示，后台补缺口；补齐后状态更新为已保存 |
| 策略研究者 | 配置研究 → 准备数据 → 预检 → 确认并运行 | 运行绑定不可变快照和工件哈希，缺数据时不能假成功 |
| 数据管理员 | 查看缺口/失败/配额 → 修复或重试 | 任务可追踪可恢复，重试只补剩余部分 |
| 运维人员 | worker/数据库重启或来源故障 | 已保存数据可继续读取，任务不重复发布，故障有原因码 |

用户无需知道 OpenBB Fetcher、数据库连接串或内部存储路径。界面可以展示“本地数据”“正在补齐”“来源延迟”“缺少某段数据”“保存失败”等与决策相关的信息。

## 3. 基本术语

- **逻辑数据集**：例如股票日线、期权链、CME 持仓；定义字段、业务键、时间与质量合同。
- **series**：一个数据集下，确定标的/市场/频率/复权/币种/数据口径/来源政策/授权共享域的记录序列。
- **覆盖**：在指定版本和请求条件下，所需观测已存在且合格；不是 `MIN/MAX` 的外包矩形。
- **新鲜**：达到该来源、市场和数据种类的更新政策；历史完整性与快照新鲜度分别判断。
- **版本**：供应商修订、复权、schema 或规范化变化后生成新内容版本；历史版本可重放。
- **就绪**：数据已持久提交、质量满足、使用获准、覆盖符合消费要求；网络请求返回不等于就绪。
- **快照**：固定 dataset version/记录 revision、工件内容哈希及研究切分；受迭代 196 的权限控制。

### 4.1 默认查询政策

新接口默认 `mode=local_first`，返回本地合格数据并自动组织必要补齐。显式 `local_only` 只查本地，保证完全离线；显式 `refresh` 在额度内刷新指定数据集/窗口，仍需校验并持久化。刷新不是删除后重下，也不是扩大到全市场扫描。

初次打开行情页可以自动查询上次选中标的和窗口；只为这一条有界查询补缺，不因浏览 tabs/下拉搜索/覆盖矩阵触发七类全量回填。重复渲染和多开页面不得反复创建相同采集工作。

旧参数 `refresh_online` 保留兼容周期，但其旧语义不改变：`false` 映射 `local_only`，`true` 映射 `refresh`；新页面显式使用新 `mode` 合同。不能把既有“false 不联网”消费者偷偷改成会联网。新默认行为通过新版本入口或显式参数启用。

### 4.2 完整性与可用性

`requested_range` 与 `effective_range` 分开。今日尚未完成的日线、未来时间和上市/退市边界不能制造假缺口；系统须说明调整原因。历史窗口已经完整时，即使今天更晚也不为该窗口无意义刷新。快照另按事件时间和抓取时间判断新鲜度。

停牌或无成交仅在有可信交易状态证据时形成已解释空缺；上游空响应不能直接证明停牌。未知缺口必须补查或标为未知。对无价格历史能力的期权链/CME 报告请求，不能自动制造 OHLC。

展示允许合格的部分数据，但研究准备默认要求所需字段、有效区间和质量 100% 满足。`warning` 不能作为忽略缺行情的通行证；可豁免条件由版本化研究政策明确规定并留痕，196 的不可豁免边界保持有效。

### 4.3 保存失败和来源错误

网络成功、落库失败时，不向客户端交付该批未保存新行作为正式市场结果；可显示此前已提交的本地数据，以及 `persist_failed` 的任务原因。若已经安全保存了原始暂存批次，重试只执行规范化/发布；若未保存，说明必须重新获取。不能用无限内存队列代替落库。

配额不足或来源不可用时返回可解释状态、下一次可尝试时间及任务摘要。内部连接串、密钥、SQL 和原始异常不返回浏览器。

## 5. 非功能需求

以下为设计验收目标，不是现有性能测量。G0 冻结硬件、存储、数据集和负载，G4 使用相同条件测量；容量变化需要重新测量。

| ID | 需求 | 必须达到的指标 |
| --- | --- | --- |
| NFR-01 | 本地性能 | 1,000 万规范 bars 基准库、20 个并发客户端、单标的 5 年日线最多 1,300 行，API P95 ≤ 500ms、P99 ≤ 1s；1,000 行分页 P95 ≤ 500ms；无全表扫描 |
| NFR-02 | 快速交互与有界请求 | 本地读/补齐受理正常情况下 ≤ 2s；页面无需等待外网才能显示已提交部分；无本地且补齐未完成返回 202/job；常规补齐任务预算默认 10 分钟 |
| NFR-03 | 网络复用和幂等 | 同窗口首次成功后重复 100 次及重启后重复调用，未到刷新条件时外部调用=0；20 个并发同缺口请求每来源最小块至多 1 次有效提取尝试（正常无故障场景），数据库重复有效行=0 |
| NFR-04 | 恢复与可用性 | worker lease 30s、heartbeat 10s、过期工作在 60s 内重新纳管；来源被阻断时所有仍满足要求的本地查询可用；不重复发布 |
| NFR-05 | 可复现性 | snapshot manifest、工件、规范记录均有 hash；冻结后重放数据内容 100% 一致；旧快照变更/缺文件必须拒绝 |
| NFR-06 | 运行环境兼容 | 主应用 MySQL、PostgreSQL、SQLite 的既有支持不退化；规范存储驱动逐引擎测试；SQLite 限单 writer 模式，不宣称具备多 worker 生产并发能力 |
| NFR-07 | 资源与运维 | 估算空间不足时回填在开始前阻断；在线队列有上限；取消/超时不留下失控子进程；至少提供 RPO≤24h、RTO≤4h 的完整数据/快照恢复演练 |
| NFR-08 | 前端可用性 | 七类切换、分页、任务重试、来源状态有键盘路径和中英文标签；旧响应不能覆盖新查询；核心组件无新增 serious/critical 可访问性问题 |

## 7. 明确的后续增强

P1 可包括按使用热度预热、冷数据 Parquet 分层、DuckDB 批分析、更多 OpenBB 供应商、完整财务修订史、外部 OpenBB Workspace widget 和 Agent 工具适配。生产分钟规模达到 DESIGN 的阈值后，再评估 ClickHouse 等专用分析存储。

本次不实现高频逐 tick 采集平台，不替换 CTP/实盘行情链，不把 LLM 用于决定是否缺行或数据是否正确，也不把 SDK/数据授权不明的来源默认启用。

## 8. 完成判定

需求全部映射到设计和具名验收，见 ACCEPTANCE 的追踪矩阵。文档通过只代表具备进入实施评审的基础；实施条件仍由 G0 现场核验，运行验收分别计算 G1—G4，不能用编译通过、HTTP 200、fixture 数据或历史运行记录替代真实数据闭环。
