# 百年老店愿景：Backtrader Web 长期发展纲要

> 版本：v1.0 | 日期：2026-05-20 | 定位：战略路线图的补充文档

---

## 核心理念：为什么要做百年老店？

量化交易平台不同于普通软件产品。它承载着用户的真金白银、交易策略（知识产权）和长期投资决策。一个量化平台如果不能持续运营，用户将面临：

- 策略迁移成本极高（代码、数据、回测结果全部丢失）
- 实盘交易中断可能造成直接经济损失
- 历史数据和研究成果无法复现

**百年老店的本质是：让用户敢于把最重要的东西托付给你。**

## 一、技术传承体系

### 1.1 代码即文档原则

| 层级 | 要求 | 当前状态 | 目标 |
|------|------|----------|------|
| 函数级 | Google-style docstring + 类型注解 | 部分覆盖 | 100% public API |
| 模块级 | 模块顶部说明文件职责 | 已有 | 保持 |
| 架构级 | ADR 记录每个重大决策 | 5 条 | 每季度 2-3 条 |
| 系统级 | project-context.md 全局视图 | 已创建 | 每月更新 |

### 1.2 知识不依赖个人

- **Bus Factor ≥ 3**：任何模块至少 3 人理解其设计意图
- **Onboarding 文档**：新开发者 1 天内能跑通全流程、3 天内能提交有意义的 PR
- **视频录制**：关键架构决策录制 15 分钟讲解视频（存档在 docs/videos/）
- **代码考古学**：git blame + ADR 让任何人都能追溯"为什么这样写"

### 1.3 技术债务管理

```text
技术债务预算：每个 Sprint 20% 时间
技术债务分类：
├── 安全债务 → 立即修复（0 容忍）
├── 性能债务 → 当季度修复
├── 可维护性债务 → 下季度修复
└── 美观性债务 → 有空再说
```

## 二、架构长寿设计

### 2.1 模块化边界

当前架构已具备良好的分层设计。百年老店视角下需要强化的是：

| 原则 | 实践 | 收益 |
|------|------|------|
| 引擎可替换 | Backtrader 通过适配器层接入，未来可换 vectorbt/自研引擎 | 不被单一引擎锁定 |
| 数据库可迁移 | SQLAlchemy 抽象层 + Alembic 迁移 | 已实现 |
| AI 模型可切换 | OpenAI-compatible 接口 + LiteLLM | 不被单一 AI 厂商锁定 |
| 前端框架可演进 | API-first 设计，前后端完全解耦 | 前端可独立重写 |
| 部署环境可迁移 | Docker + Helm，不绑定特定云 | 用户自主可控 |

### 2.2 API 稳定性契约

```text
API 版本策略：
├── /api/v1/* → 当前稳定版，承诺 24 个月向后兼容
├── /api/v2/* → 下一代（2026 Q2 发布），v1 进入 deprecated
├── 废弃流程：标记 deprecated → 12 个月过渡期 → 移除
└── Breaking change：必须有迁移指南 + 自动化迁移脚本
```

### 2.3 数据持久性保证

- **策略代码**：Git 版本控制 + 数据库双重存储
- **回测结果**：结构化存储 + 可导出（JSON/CSV）
- **用户数据**：定期备份 + 导出 API（用户有权带走自己的数据）
- **历史行情**：本地缓存 + 多数据源冗余

## 三、社区可持续性

### 3.1 治理模型演进

```text
阶段 1（当前）: BDFL（仁慈独裁者）模式
    └── 创始人主导决策，快速迭代

阶段 2（500+ Stars）: 核心维护者委员会
    ├── 3-5 名核心维护者
    ├── RFC 流程处理重大变更
    └── 季度路线图公开投票

阶段 3（5000+ Stars）: 基金会模式
    ├── 成立开源基金会（或加入现有基金会）
    ├── 独立于任何单一公司
    ├── 透明的财务和决策
    └── 商标和品牌保护
```

### 3.2 贡献者成长路径

```text
新手贡献者 → 活跃贡献者 → 模块维护者 → 核心维护者 → 治理委员会
    │              │              │              │
    ├── good-first-issue  ├── 代码审查权  ├── 发布权限  ├── 战略决策
    ├── 文档修复          ├── Issue 分类  ├── 路线图投票 ├── 财务管理
    └── 小 bug 修复       └── 导师角色    └── ADR 审批   └── 品牌管理
```

### 3.3 社区健康指标

| 指标 | 健康阈值 | 告警阈值 |
|------|----------|----------|
| Issue 首次响应时间 | < 48h | > 7 天 |
| PR 审查时间 | < 5 天 | > 14 天 |
| 月度新贡献者 | ≥ 2 | 0 |
| 核心维护者活跃度 | 每周有提交 | 连续 2 周无活动 |
| 文档更新频率 | 每月 | 超过 3 个月未更新 |

## 四、商业可持续性

### 4.1 开源与商业的平衡

```text
开源核心（MIT）                    商业增值
├── 回测引擎                       ├── 云托管服务
├── 策略管理                       ├── 企业级 SLA
├── 基础 AI 助手                   ├── 高级 AI 模型
├── 单用户部署                     ├── 多租户管理
├── 社区数据源                     ├── 专业数据源
└── 基础风控                       └── 企业级风控 + 合规
```

**原则**：核心功能永远开源，商业化只做增值服务。用户永远可以自己部署完整功能。

### 4.2 收入多元化

| 收入来源 | 占比目标 | 风险等级 | 启动时间 |
|----------|----------|----------|----------|
| SaaS 订阅 | 40% | 中 | Phase 2 |
| 策略市场佣金 | 25% | 中 | Phase 3 |
| 企业定制 | 20% | 低 | Phase 3 |
| 教育培训 | 10% | 低 | Phase 4 |
| 数据市场 | 5% | 高 | Phase 4 |

### 4.3 财务纪律

- **18 个月现金储备**：任何时候都保持 18 个月运营资金
- **盈利优先于增长**：不烧钱换用户，追求健康的单位经济模型
- **开源不等于免费劳动**：核心维护者应获得合理报酬
- **透明财务**：定期公开收支报告（基金会阶段）

## 五、质量文化

### 5.1 质量金字塔

```text
                    ┌─────────────┐
                    │  用户体验   │  ← NPS > 50
                    ├─────────────┤
                    │  功能正确性 │  ← 零资金损失 bug
                    ├─────────────┤
                    │  性能可靠性 │  ← 99.9% 可用性
                    ├─────────────┤
                    │  代码质量   │  ← 85%+ 覆盖率
                    ├─────────────┤
                    │  安全合规   │  ← 零已知漏洞
                    └─────────────┘
```

### 5.2 不可妥协的底线

1. **资金安全**：任何可能导致用户资金损失的 bug 都是 P0，24 小时内修复
2. **数据完整性**：用户的策略代码和回测数据永远不能丢失
3. **隐私保护**：用户的交易策略是核心机密，平台不得泄露或利用
4. **向后兼容**：已发布的 API 至少保持 12 个月兼容期
5. **透明沟通**：出了问题第一时间告知用户，不隐瞒

### 5.3 持续改进机制

- **季度架构审查**：每季度一次全面架构健康检查
- **年度安全审计**：每年一次第三方安全渗透测试
- **用户反馈闭环**：每个用户反馈都有跟踪和回复
- **技术雷达**：每半年评估新技术的采纳价值

## 六、长期技术演进路线

### 10 年视角

| 时间 | 里程碑 | 关键能力 |
|------|--------|----------|
| 2026 | v2.0 发布 | 稳定可靠的基础平台 |
| 2027 | AI-Native | 智能策略生成 + 风控 |
| 2028 | 平台化 | 策略市场 + 插件生态 |
| 2029 | 全球化 | 多语言 + 多地区合规 |
| 2030 | 机构级 | 大型基金可用的稳定性 |
| 2031-2035 | 行业标准 | 成为量化教育和研究的标准工具 |
| 2036+ | 基础设施 | 像 Git 之于代码一样，成为量化交易的基础设施 |

### 技术演进原则

1. **渐进式替换**：永远不做大规模重写，用 Strangler Fig 模式逐步替换
2. **标准优先**：优先采用行业标准（OpenAPI、OpenTelemetry、FIX 协议）
3. **向前兼容设计**：今天的设计要为 5 年后的需求留出空间
4. **简单胜于复杂**：能用简单方案解决的问题，不引入复杂架构

## 七、风险免疫体系

### 7.1 单点故障消除

| 风险点 | 当前状态 | 免疫措施 |
|--------|----------|----------|
| 创始人离开 | 高风险 | 文档化所有决策 + 培养核心维护者 |
| 关键依赖停更 | 中风险 | 适配器模式隔离 + 备选方案评估 |
| 云服务商锁定 | 低风险 | Docker + Helm，多云兼容 |
| 数据源中断 | 中风险 | 多数据源冗余 + 本地缓存 |
| 监管政策变化 | 中风险 | 模块化设计，可按地区禁用功能 |

### 7.2 灾难恢复

- **代码**：GitHub + 镜像仓库（Gitee）+ 本地备份
- **数据**：自动备份 + 异地存储 + 定期恢复演练
- **知识**：文档 + ADR + 视频 + 社区知识库
- **品牌**：商标注册 + 域名多年续费 + 社交账号矩阵
